# AI Space Research Assistant

A local Retrieval-Augmented Generation (RAG) application for asking questions about NASA technical documentation.

The system retrieves relevant passages from the **NASA Systems Engineering Handbook**, then provides those passages as context to a locally hosted **Qwen3** language model. Answers include source-page information, and low-relevance queries are rejected instead of being passed to the LLM.

## Demo

The application provides a web interface where users can:

- Ask questions about NASA systems engineering
- Receive grounded answers generated from the handbook
- View the source pages used for the response
- Receive a clear refusal when the retrieved context is not relevant

## RAG Pipeline

The project follows a simple retrieval-augmented generation pipeline:

```text
NASA PDF
   ↓
Text Extraction
   ↓
Chunking
   ↓
Sentence Transformer Embeddings
   ↓
ChromaDB Vector Store
   ↓
Semantic Retrieval (Top 5)
   ↓
Relevance Check
   ↓
Relevant Context
   ↓
Qwen3 1.7B
   ↓
Answer + Source Pages
```

### 1. Document processing

The NASA Systems Engineering Handbook is extracted into page-level text.

The handbook contains selectable text, so the final pipeline uses direct text extraction rather than OCR.

### 2. Chunking

The extracted text is split into overlapping chunks to make retrieval more precise.

Current configuration:

- Chunk size: 1000 characters
- Overlap: 200 characters
- Sentence-aware splitting

This produced **1,185 chunks** from the handbook.

### 3. Embeddings

Each chunk is converted into a vector using:

**`all-MiniLM-L6-v2`**

The embedding model maps semantically similar text to nearby vectors.

### 4. Vector storage and retrieval

Embeddings are stored in **ChromaDB**.

For each user question:

1. The question is embedded.
2. ChromaDB performs semantic similarity search.
3. The top 5 results are retrieved.
4. Retrieved metadata provides the source document and page number.

### 5. Relevance guard

Before calling the LLM, the application checks the best retrieval distance.

If the best retrieved distance is above the relevance threshold, the query is rejected:

```text
"The information is not available in the provided context."
```

This prevents obviously unrelated questions from being passed to the language model.

The current threshold is:

```text
RELEVANCE_THRESHOLD = 1.0
```

### 6. Grounded generation

Relevant chunks are passed to a locally running **Qwen3 1.7B** model through Ollama.

The generation prompt instructs the model to answer using only the supplied context.

Temperature is set to `0` for more deterministic generation.

### 7. Source attribution

Source pages are generated by the application from the retrieved ChromaDB metadata rather than asking the LLM to invent page numbers.

This makes citation generation deterministic.

## Evaluation

The project includes a small evaluation set containing:

- 9 answerable questions
- 1 unsupported question

Current baseline results:

| Metric | Result |
|---|---:|
| Answerable-question keyword coverage | **89%** |
| Retrieval expected-page hit | **100%** |
| Unsupported-query rejection | **100%** |

These results are from a small development evaluation set and should not be interpreted as general model accuracy.

The evaluation script is:

```text
evaluate_handbook_rag.py
```

## Engineering Decisions

This project was developed iteratively rather than simply connecting a PDF to an LLM.

### Retrieval depth

The initial retriever returned 3 chunks.

Testing broader questions showed that increasing this to 5 improved context coverage without introducing obvious unsupported information.

### Grounding protection

An unsupported question about Apollo spacecraft thrust produced a poor semantic match with a best distance around `1.33`.

With the `1.0` relevance threshold, the system rejects the query before calling the LLM.

### Citation reliability

Initially, page citations were generated by the LLM.

Because a small local model could produce inconsistent citations, citation generation was moved into the application layer using retrieved metadata.

### Separation of concerns

The backend is split into focused components:

```text
retriever.py
    → semantic search

generator.py
    → LLM generation

rag.py
    → retrieval + grounding + orchestration

app.py
    → HTTP API
```

This keeps retrieval, generation, RAG logic, and API concerns separate.

## Local Setup

### Prerequisites

Install:

- Python 3.11+
- Node.js
- Ollama
- Git

### 1. Clone the repository

```bash
git clone https://github.com/kumarv34605-star/AI-Space-Research-Assistant.git
cd AI-Space-Research-Assistant
```

### 2. Create the Python environment

Windows PowerShell:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
```

Install dependencies:

```powershell
pip install -r requirements.txt
```

### 3. Download the Qwen model

Install and configure Ollama, then:

```powershell
ollama pull qwen3:1.7b
```

### 4. Prepare the document database

Place the NASA Systems Engineering Handbook PDF in:

```text
data/raw/
```

Then run:

```powershell
python extract_text.py
python chunking_handbook.py
python ingest_handbook.py
```

This extracts the handbook, creates the chunks, generates embeddings, and stores them in ChromaDB.

### 5. Start the backend

```powershell
uvicorn app:app --reload
```

The API will be available at:

```text
http://127.0.0.1:8000
```

Swagger API documentation:

```text
http://127.0.0.1:8000/docs
```

### 6. Start the frontend

Open another terminal:

```powershell
cd frontend
npm install
npm run dev
```

The frontend will provide the browser interface for asking questions.

## API

### `GET /`

Health check:

```json
{
  "message": "AI Space Research Assistant API is running"
}
```

### `POST /ask`

Request:

```json
{
  "question": "What is verification?"
}
```

Response:

```json
{
  "question": "What is verification?",
  "answer": "...",
  "sources": [
    {
      "page": 100,
      "source": "NASA Systems Engineering Handbook"
    }
  ]
}
```

The API validates empty questions and returns HTTP `400` for invalid input.

## Docker

The backend includes a Dockerfile for containerized deployment.

Build:

```powershell
docker build -t ai-space-research-assistant .
```

Run:

```powershell
docker run --rm -p 8000:8000 `
  -e OLLAMA_URL="http://host.docker.internal:11434/api/generate" `
  -v "${PWD}\chroma_db:/app/chroma_db" `
  ai-space-research-assistant
```

The ChromaDB directory is mounted at runtime instead of being baked into the image.

For development on lower-memory machines, running FastAPI and Ollama directly on the host can reduce resource pressure.
